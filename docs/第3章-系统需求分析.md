# 第3章　系统分析

## 3.1 系统分析概述

在冷库设备综合运维管理系统的设计与开发过程中，结合冷链仓储行业对设备可靠性与故障处置时效的现实要求，围绕冷库现场设备台账管理、故障报修与维修闭环、预防性维保以及备件库存协同等核心业务开展需求分析。通过对冷库运维场景的业务梳理与角色访谈，将系统使用对象归纳为管理员、运维人员与甲方用户三类角色，并据此形成如下核心需求：

（1）甲方用户层面，系统需要为其提供便捷的设备查看与故障报修入口。甲方可浏览系统内全部设备（含公共设备），选择目标设备填写故障描述并上传现场图片发起报修；可查看本人提交工单的处理进度，对“待验收”工单确认完工，并对已完成工单进行评价。同时支持个人中心维护基础资料与修改密码，以及接收与工单相关的消息提醒。

（2）运维人员层面，系统需要支撑其完成指派范围内的现场处置工作。运维可查看待办与已指派工单，执行接单、过程填报、备件领用、提交完工等操作；可维护故障记录与检索故障案例库；可执行维保任务填报；可参与备件出入库相关业务；可在运维工作台查看个人待办摘要与临近维保提醒；并可接收派单、维保指派等实时消息。

（3）管理员层面，系统需要覆盖平台配置与全流程管控能力。管理员负责用户与权限管理、冷库/冷藏间/设备台账维护、工单派单转派撤回关闭、维保计划制定与任务指派、供应商与备件档案管理、设备健康分析与全局数据统计，以及操作日志审计。同时负责系统级消息触达与导入导出等支撑能力，保障业务闭环可追溯、可统计、可扩展。

## 3.2 系统功能性需求分析

### 3.2.1 甲方用户的功能分析

甲方用户是冷库现场使用方的业务发起者之一。甲方用户在系统中可进行设备浏览与报修、本人工单跟踪与验收评价、个人中心维护以及消息查看等核心用例操作。甲方用户用例图分析如图3.2所示。

**图3.2　甲方用户用例图**

#### （1）登录与退出

甲方用户通过用户名与密码登录系统，系统校验账号状态并签发 Token。登录成功后按角色展示菜单；退出登录时清除本地会话，并将 Token 写入黑名单以防复用。该用例保障身份真实与会话可控。

#### （2）浏览设备台账

甲方用户可按设备编号、名称、冷藏间、类型、状态等条件查询设备列表，查看设备详情中的基础档案信息。甲方不可新增、编辑或删除设备，但可查看全部设备（含公共设备），以便准确选择报修对象。浏览设备台账用例图如图3.3所示。

**图3.3　浏览设备台账用例图**

#### （3）提交报修工单

提交报修是甲方用户的核心用例。甲方选择设备后填写故障描述，可上传现场图片，系统生成唯一工单号，工单初始状态为“待受理”，并联动设备进入故障相关状态，同时向管理员推送新报修消息。提交报修工单用例图如图3.4所示。

**图3.4　提交报修工单用例图**

#### （4）查看本人工单进度

甲方仅可查看本人提交的工单列表与详情，包括状态流转、指派运维、处理过程、维修图片与备件使用等信息，便于跟踪处置进度。

#### （5）确认验收与服务评价

当工单处于“待验收”时，甲方可确认完工，工单进入“已完成”，设备恢复正常运行状态，并向对应运维推送验收完成消息。对已完成工单，甲方可进行满意度评价并填写评价内容，工单进入“已评价”。

#### （6）维护个人信息

甲方可在个人中心查看账号信息、修改姓名与联系方式、修改登录密码；可查看管理员绑定的冷藏间归属信息（仅展示，不作为设备可见范围限制）。

#### （7）消息中心

甲方可查看与本人相关的系统消息（如工单待验收提醒），支持标记已读与全部已读；前端可通过 WebSocket 接收实时推送并展示未读角标。

---

### 3.2.2 运维人员的功能分析

运维人员是故障处置与预防性维保的执行主体。运维人员可在系统中处理指派工单、维护故障与案例、执行维保任务、参与备件业务，并使用运维工作台与消息提醒提升响应效率。运维人员用例图分析如图3.5所示。

**图3.5　运维人员用例图**

#### （1）运维工作台

运维登录后可查看个人待处理工单数量、本月完成数量以及临近维保提醒清单，快速进入对应业务页面，形成“先看待办、再去处置”的使用路径。

#### （2）处理运维工单

处理运维工单是运维核心用例。运维对“已派单”工单执行接单，进入“处理中”；填写处理过程、故障类型/原因、处理方案、维修耗时，可上传维修图片并登记使用备件（联动库存出库）；提交完工后工单进入“待验收”。列表可查看较广范围工单，但接单与过程提交等处理类操作仅限管理员指派给本人的工单。处理运维工单用例图如图3.6所示。

**图3.6　处理运维工单用例图**

#### （3）故障记录管理

运维可新增、编辑故障记录，关联设备与工单，记录故障类型、等级、现象、原因、方案、起止时间与图片等，形成可检索的故障台账，为后续统计分析与案例沉淀提供数据基础。

#### （4）故障案例库检索与维护

运维可按设备类型、故障类型与关键词检索历史案例，获取排查方法与处理方案参考。经授权后可维护案例内容，实现经验复用（非 AI 生成）。

#### （5）维保任务执行

运维对指派给本人的维保任务填写检查项结果、异常情况、处理措施与备件使用，完成后更新任务状态。该用例与故障维修工单相互独立，体现预防性维护业务。

#### （6）备件与供应商协同

运维可查询备件库存与出入库流水，在工单/维保领用场景下触发出库；可查看供应商基础信息，保障备件来源可追溯。当库存低于安全库存时，系统向管理员发送库存不足消息。

#### （7）设备与冷库浏览

运维可浏览冷库、冷藏间与设备台账，查看设备生命周期状态历史、维修档案摘要与健康分析结果，辅助判断设备风险并安排处置优先级。

#### （8）消息中心

运维可接收工单派单/转派、维保任务指派等消息，支持未读统计、已读标记与 WebSocket 实时提醒。

### 3.2.3 管理员的功能分析

管理员是保障系统规范运行、贯通全业务闭环的核心角色。管理员负责基础数据配置、工单全流程管控、维保计划管理、库存与供应商治理、健康与统计分析，以及用户权限与审计。管理员用例图分析如图3.7所示。

**图3.7　管理员用例图**

#### （1）用户与权限管理

管理员可对用户进行增删改查、角色分配（管理员/运维/甲方）、启用与禁用；可为甲方绑定冷藏间用于归属展示。该用例保证账号可控、权限清晰。管理用户用例图如图3.8所示。

**图3.8　管理用户用例图**

#### （2）冷库与冷藏间管理

管理员维护冷库基础档案（名称、地址、联系人、状态等），维护下属冷藏间（编码、温度范围、容积等）。进入库区详情时，以“单库办事台”方式展示本库待办工单、异常设备与临近维保，强调现场处置入口而非报表分析。

#### （3）设备台账与生命周期管理

管理员（及运维）可维护设备档案，支持多条件查询、详情、报废/恢复等状态变更，并记录状态历史。工单报修、处理、验收等节点自动联动设备状态。设备台账支持 Excel 导入与导出，便于批量建档。设备台账管理用例图如图3.9所示。

**图3.9　设备台账管理用例图**

#### （4）工单全流程管控

管理员可查看全平台工单，执行派单、转派、撤回、关闭、重开与归档等操作；派单后向运维推送提醒。工单状态机为：待受理 → 已派单 → 处理中 → 待验收 → 已完成 → 已评价 → 已归档。工单全流程管控用例图如图3.10所示。

**图3.10　工单全流程管控用例图**

#### （5）维保计划与任务管理

管理员制定月度/季度/半年度/年度维保计划，配置检查项并生成维保任务，可指派运维执行并跟踪完成情况，与故障维修工单形成双轨运维机制。

#### （6）备件、供应商与库存预警

管理员维护供应商与备件档案，执行入库、出库、盘点与调整并保留流水；设置安全库存，库存不足时触发消息预警，保障维修物料供给。

#### （7）设备健康分析与维修档案

系统按规则统计近一年故障次数等指标，输出健康等级（正常/关注/预警），并在设备详情汇总故障、维修、维保与备件消耗档案，为更换决策提供依据（规则计算，非 AI）。

#### （8）数据统计中心

管理员进入全系统“分析台”，按时间查看工单完成率、平均响应/维修时长、故障类型分布、冷库对比、库存不足与维保任务完成情况等 ECharts 图表，与库区详情的“当下待办”形成互补。

#### （9）操作日志与消息中心

管理员可查询关键操作日志（登录、派单、库存变动等），实现审计追溯；可查看系统消息并管理已读状态，保障运营通知可达。

## 3.3 系统非功能性需求分析

### 3.3.1 可用性

系统面向冷库管理人员、现场运维与甲方用户设计 Web 端界面，采用统一导航与表格筛选交互。核心流程（报修—派单—处理—验收、维保任务填报、出入库）步骤清晰；列表支持多条件查询与分页；统计页提供图表化展示。消息中心结合角标与实时推送，降低漏看待办的概率。

### 3.3.2 安全性

用户密码采用 BCrypt 加密存储，避免明文落库。系统基于 JWT 进行身份认证，并通过拦截器校验接口访问；退出登录后将 Token 加入黑名单（Redis 可用时写入缓存，不可用时降级本地缓存）。按管理员、运维、甲方划分菜单与接口权限：甲方工单仅限本人单据；运维处理类操作仅限指派给本人的工单/维保任务；管理员拥有全量管控权限。关键业务写入操作日志，保证可追溯。

### 3.3.3 可靠性

工单状态流转、库存扣减、设备状态联动等关键路径采用服务端校验与事务控制，防止非法跳转状态或超卖库存。对异常请求返回明确业务提示。Redis 连接失败时自动降级，避免因缓存不可用导致接口长时间阻塞，保障系统在基础环境下仍可稳定提供业务服务。

### 3.3.4 可扩展性

系统采用前后端分离架构，后端按认证、冷库、设备、工单、故障、维保、备件、统计、消息等模块划分，接口遵循 REST 风格统一返回格式。后续可在不大改主体结构的前提下扩展更多设备类型字典、维保模板、报表维度或对接外部通知通道。

### 3.3.5 可维护性

前后端代码按业务模块组织，前端路由与菜单按角色配置，后端 Service 封装业务规则，Mapper 访问数据库，降低模块耦合。配置项（数据源、JWT、上传目录、Redis 开关等）集中于配置文件，便于部署与环境切换。数据库变更通过迁移脚本管理，便于版本演进与问题定位。

---

## 3.4 本章小结

本章围绕冷库设备综合运维管理系统，从管理员、运维人员与甲方用户三类角色出发，完成了系统分析概述与功能性需求分析，并通过用例描述明确了报修闭环、维保双轨、备件库存、健康分析、统计中心与消息提醒等核心业务边界；同时从可用性、安全性、可靠性、可扩展性与可维护性五个方面给出了非功能性需求。上述分析为后续系统总体设计、数据库设计与功能实现提供了依据。
